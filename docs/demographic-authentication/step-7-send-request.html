Step 7 - Send Authentication Request

Goal​

After the Authentication Request XML has been successfully generated and digitally signed, the next step is to send the authentication request to the AUA Server.

In the Sub-AUA architecture, the Sub-AUA does not directly send the Authentication Request to the UIDAI Authentication Server.

The request follows this flow:

Sub-AUA
    │
    │ Sub-AUA Request
    ▼
AUA Server
    │
    │ Final UIDAI Authentication Request
    ▼
ASA
    │
    ▼
UIDAI Authentication Server

The Sub-AUA sends the authentication request to the AUA using a secure HTTPS connection.

Request Flow​

Authentication Request XML
        │
        ▼
Digitally Sign XML
        │
        ▼
Generate Request Hash
        │
        ▼
Create Sub-AUA Request
        │
        ├── client_id
        ├── req_hash
        └── req_data
        │
        ▼
Send HTTPS POST Request
        │
        ▼
AUA Server
        │
        ▼
AUA Validates Request
        │
        ▼
AUA Processes Authentication Request
        │
        ▼
AUA Sends Request to UIDAI

Step 1 - Prepare the Authentication Request XML​

The Sub-AUA first creates the complete Authentication Request XML.

The XML contains all required authentication information, such as:

  • Authentication details
  • Authentication factors
  • Device information (if applicable)
  • Encrypted Session Key
  • Encrypted PID
  • HMAC
  • Digital Signature

The final Authentication XML should be generated according to the authentication method being used.

For example:

<Auth>
    ...
    <Uses>
        ...
    </Uses>

    <Device>
        ...
    </Device>

    <Skey>
        ...
    </Skey>

    <Data>
        ...
    </Data>

    <Hmac>
        ...
    </Hmac>

    <Signature>
        ...
    </Signature>
</Auth>

The exact Authentication XML structure depends on the Aadhaar Authentication API specification and the authentication method being used.

Step 2 - Generate Request Hash​

After creating the final Authentication Request XML, generate the request hash.

The request hash is generated from the Authentication Request XML according to the hashing mechanism defined by the Sub-AUA-to-AUA integration.

Example Base64-encoded hash:

BASE64_ENCODED_REQUEST_HASH

The hash allows the AUA to verify the integrity of the request data received from the Sub-AUA.

The request hash must correspond to the request data being sent in req_data.

Step 3 - Create Sub-AUA Request​

The Sub-AUA creates the request that will be sent to the AUA.

The request contains three main fields:

FieldDescription
client_idUnique identifier assigned to the Sub-AUA/client by the AUA
req_hashHash generated from the request data
req_dataFinal Authentication Request XML or request data

The request structure is:

<xml>
    <client_id>AUA-CHP</client_id>

    <req_hash>
        BASE64_ENCODED_REQUEST_HASH
    </req_hash>

    <req_data>
        <!-- Digitally Signed Authentication Request XML -->
    </req_data>
</xml>

The req_data field contains the final authentication request generated by the Sub-AUA.

The exact XML or JSON wrapper structure should follow the API contract provided by the AUA.

Step 4 - Send Request to AUA​

The Sub-AUA sends the prepared request to the AUA Server using HTTPS.

HTTP Method​

POST

Example Endpoint​

https://aua.example.com/api/authentication

Replace the endpoint with the actual API endpoint provided by the AUA.

HTTP Headers​

Content-Type: application/xml
Accept: application/xml

Request Body​

The Sub-AUA sends the following request to the AUA:

<?xml version='1.0' encoding='utf-8'?>
<xml>
    <client_id>AUA-CHP</client_id>

    <req_hash>
        BASE64_ENCODED_REQUEST_HASH
    </req_hash>

    <req_data>
        Signed Authentication Request XML
    </req_data>
</xml>

The actual req_data should contain the complete digitally signed Authentication Request XML.

The complete flow is:

What Happens at the AUA?​

After receiving the request, the AUA performs the required validation.

The AUA may:

  1. Validate the client_id.
  2. Validate the Sub-AUA credentials.
  3. Verify the req_hash.
  4. Verify the integrity of req_data.
  5. Validate the Authentication Request XML.
  6. Validate the digital signature.
  7. Add or update required AUA-specific information.
  8. Forward the final authentication request to the ASA.
  9. Receive the Authentication Response from UIDAI.
  10. Return the response to the Sub-AUA.

Important: Sub-AUA Request vs UIDAI Request​

There are two separate requests in this architecture.

Request 1 - Sub-AUA to AUA​

Sub-AUA
    │
    │ client_id
    │ req_hash
    │ req_data
    ▼
AUA

Request 2 - AUA to UIDAI​

AUA
    │
    │ Final Authentication XML
    │ Digital Signature
    ▼
ASA
    │
    ▼
UIDAI

The Sub-AUA should not assume that the request sent to the AUA is identical to the final request sent by the AUA to UIDAI.

The AUA is responsible for handling the UIDAI-specific integration and communication with the ASA.

Validation Checklist​

Before sending the request to the AUA, verify that:

  • The Authentication Request XML is complete.
  • The Authentication XML has been digitally signed.
  • The request hash has been generated correctly.
  • client_id is valid.
  • req_hash corresponds to the correct request data.
  • req_data contains the correct Authentication Request XML.
  • The request is sent over HTTPS.
  • The HTTP method is POST.
  • The correct AUA endpoint is being used.
  • A unique Transaction ID is used for the authentication request.

Common Errors​

ErrorPossible Cause
Invalid client_idSub-AUA/client identifier is invalid
Invalid req_hashHash does not match the request data
Invalid req_dataRequest data is malformed or incomplete
Invalid XMLAuthentication XML is not well-formed
Invalid SignatureDigital signature verification failed
UnauthorizedSub-AUA is not authorized to use the AUA service
Connection FailedAUA endpoint is unavailable
Request TimeoutAUA server did not respond within the expected time

Best Practices​

  • Always communicate with the AUA using HTTPS.
  • Never send authentication data over an unsecured connection.
  • Generate a unique Transaction ID for every authentication request.
  • Generate the request hash from the correct request data.
  • Ensure that req_hash and req_data always correspond to each other.
  • Do not modify req_data after generating the request hash.
  • Do not log sensitive authentication data.
  • Handle AUA error responses properly.
  • Implement appropriate timeout handling.
  • Do not blindly retry authentication requests without considering transaction duplication.

Output of this Step​

After completing this step:

Sub-AUA
    │
    │ client_id
    │ req_hash
    │ req_data
    ▼
AUA Server

The AUA receives the authentication request and begins processing it.

The AUA then handles the communication with the ASA and UIDAI Authentication Server.

Next Step​

Continue to Step 8 - Receive Authentication Response.

The AUA will return the authentication response to the Sub-AUA after processing the request.

The Sub-AUA should parse the response and determine whether the authentication was successful or failed.

Notes​

In a Sub-AUA architecture, the request sent by the Sub-AUA to the AUA is an integration layer between the Sub-AUA and AUA. The exact request wrapper, including fields such as client_id, req_hash, and req_data, is defined by the AUA's integration API.

The req_data field should contain the authentication request data agreed upon between the Sub-AUA and AUA. If the AUA requires the complete digitally signed Authentication XML, the Sub-AUA should provide that XML in req_data.

The Sub-AUA-to-AUA request and the AUA-to-UIDAI request are separate communication layers and should be documented separately.
