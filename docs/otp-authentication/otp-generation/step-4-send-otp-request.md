# Step 4 - Send OTP Request

## Goal

After generating and digitally signing the OTP Request XML, the next step is to send the request securely to the **AUA Server** using an HTTPS `POST` request.

In the Sub-AUA architecture, the Sub-AUA does not directly send the OTP Request to the UIDAI Authentication Server.

The Sub-AUA sends the OTP request to the AUA. The AUA processes the request and handles the communication with the UIDAI authentication infrastructure.

The request flow is:

```text
Sub-AUA
    │
    │ HTTPS POST
    │ client_id
    │ req_hash
    │ req_data
    ▼
AUA Server
    │
    │ Process / Validate Request
    ▼
UIDAI Authentication Infrastructure
    │
    ▼
OTP Response
    │
    ▼
AUA Server
    │
    ▼
Sub-AUA
```

---

## Prerequisites

Before sending the request, ensure that:

* The OTP Request XML has been generated successfully.
* The XML has been digitally signed.
* The `client_id` provided by the AUA is valid.
* The request hash (`req_hash`) has been generated correctly.
* The `req_hash` corresponds to the request data being sent in `req_data`.
* The AUA endpoint is correctly configured.
* A secure HTTPS connection is being used.
* The required HTTP headers are configured.

---

## HTTP Method

The Sub-AUA sends the request to the AUA using the HTTP `POST` method.

```http
POST
```

---

## Request URL

Send the request to the OTP endpoint provided by the AUA.

Example:

```text
https://aua.example.com/api/otp
```

> Replace the example URL with the actual endpoint provided by your AUA.

---

## HTTP Headers

Typical request headers:

```http
Content-Type: application/xml
Accept: application/xml
```

Depending on the AUA integration, additional HTTP headers may also be required.

---

## Request Body

The Sub-AUA request is wrapped inside an `<xml>` root element.

The request contains the following fields:

| Field | Description |
|---|---|
| `client_id` | Identifier provided by the AUA for the Sub-AUA/client |
| `req_hash` | Hash generated for the request data |
| `req_data` | Digitally signed OTP Request XML |

Example:

```xml
<?xml version='1.0' encoding='utf-8'?>
<xml>
    <client_id>AUA-CHP</client_id>

    <req_hash>
        BASE64_ENCODED_REQUEST_HASH
    </req_hash>

    <req_data>
        Signed OTP Request XML
    </req_data>
</xml>
```

The `req_data` field contains the OTP Request XML generated and digitally signed by the Sub-AUA.

> The exact format and encoding of `req_data` should follow the API contract provided by the AUA.

## Example OTP Request

The complete request sent by the Sub-AUA to the AUA can be represented as:

```xml
<?xml version='1.0' encoding='utf-8'?>
<xml>
    <client_id>AUA-CHP</client_id>

```

## What Happens on the AUA Server?

After receiving the request, the AUA server performs the required validation and processing.

The AUA may:

1. Validate the `client_id`.
2. Validate the Sub-AUA credentials.
3. Verify the `req_hash`.
4. Validate the `req_data`.
5. Validate the OTP Request XML.
6. Verify the digital signature.
7. Validate the request parameters.
8. Process the OTP generation request.
9. Forward the appropriate request to the UIDAI authentication infrastructure.
10. Receive the OTP Response.
11. Return the OTP Response to the Sub-AUA.

## Request Flow Between Sub-AUA, AUA and UIDAI

There are two separate communication layers.

### Request 1 - Sub-AUA to AUA

```text
Sub-AUA
    │
    │ HTTPS POST
    │
    │ client_id
    │ req_hash
    │ req_data
    ▼
AUA Server
```

The Sub-AUA sends the OTP request to the AUA using the integration API provided by the AUA.

---

### Request 2 - AUA to UIDAI

```text
AUA
    │
    │ OTP Request
    ▼
UIDAI Authentication Infrastructure
```

The AUA handles the UIDAI-specific integration and communication with the authentication infrastructure.

## Validation Checklist

Before sending the request, verify that:

* The OTP Request XML is well-formed.
* The XML has been digitally signed.
* The `client_id` is valid.
* The `req_hash` has been generated correctly.
* The `req_hash` corresponds to the correct `req_data`.
* The `req_data` contains the correct signed OTP Request XML.
* The Transaction ID is unique.
* The timestamp is current.
* HTTPS is being used.
* SSL/TLS certificate validation is enabled.
* The correct AUA endpoint is configured.

---

## Common Errors

| Error | Possible Cause |
|---|---|
| Invalid `client_id` | Sub-AUA/client identifier is invalid |
| Invalid `req_hash` | Hash does not match the request data |
| Invalid `req_data` | Request data is malformed or incomplete |
| HTTP 400 | Invalid XML or malformed request |
| HTTP 401 | Invalid credentials or authentication failure |
| HTTP 403 | Access denied |
| HTTP 404 | Incorrect AUA endpoint URL |
| HTTP 500 | Internal server error |
| Connection Timeout | Network issue or server unavailable |
| SSL/TLS Error | Certificate validation failed |
| Invalid Signature | Digital signature verification failed |

---

## Best Practices

* Always use HTTPS to protect data in transit.
* Set an appropriate request timeout.
* Generate a unique Transaction ID for every OTP request.
* Generate the request hash from the correct request data.
* Ensure that `req_hash` and `req_data` always correspond to each other.
* Do not modify `req_data` after generating the request hash.
* Log only non-sensitive request information such as the Transaction ID and timestamp.
* Never log Aadhaar numbers, OTP values, signed XML, or other sensitive authentication data in production logs.
* Retry requests only for temporary network failures.
* Do not blindly retry OTP requests, as this may result in generating multiple OTPs or invalidating a previously generated OTP.

## Output of this Step

After successfully sending the request:

```text
Sub-AUA
    │
    │ client_id
    │ req_hash
    │ req_data
    ▼
AUA Server
```

The AUA receives the OTP request and begins processing it.

The AUA then handles the communication with the UIDAI authentication infrastructure.

After processing the request, the OTP response is returned to the Sub-AUA.

The response indicates whether the OTP generation request was successful or failed.

## Next Step

Continue to **Step 5 - Receive OTP Response**.

The Sub-AUA will receive the OTP Response from the AUA after the OTP generation request has been processed.

The Sub-AUA should parse the response and determine whether the OTP request was successful or failed.

---

## Notes

> In a Sub-AUA architecture, the request sent by the Sub-AUA to the AUA is an integration layer between the Sub-AUA and AUA. The exact request wrapper, including fields such as `client_id`, `req_hash`, and `req_data`, is defined by the AUA's integration API.

> The `req_data` field should contain the OTP request data agreed upon between the Sub-AUA and AUA. If the AUA requires the complete digitally signed OTP Request XML, the Sub-AUA should provide that XML in `req_data`.

> The Sub-AUA-to-AUA request and the AUA-to-UIDAI request are separate communication layers and should be documented separately.

> The OTP Request flow described in this document applies to the Sub-AUA integration layer. The exact AUA-to-UIDAI communication process depends on the AUA/ASA integration and the applicable UIDAI API specification.
